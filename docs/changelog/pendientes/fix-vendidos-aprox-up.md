- **2026-10-28** — issue #251 (smoke de Mateo, ext 0.3.36): ficha `/up/MCOU2401140163` ("Almohada Cojín Dona Para Hemorroides Coxis", Full, "+1000 vendidos" visible) mostraba "Vendidos (exacto) 1000" / "Ventas/mes 24" / "Facturación $2.031.706" — Selltrix, para la misma publicación, muestra 2.200 vendidos (1000 × 2.2 Full), 50/mes, $4.279.716 (antigüedad 3.6 a).

  **Causa real**: Mercado Libre ya no muestra ningún conteo exacto de ventas en la interfaz (solo el piso redondeado "+N vendidos" — confirmado desde el issue #174) — pero para publicaciones de alto volumen, ese MISMO piso redondeado se filtra también al `sold_quantity` del JSON que la propia página incrusta (`__NORDIC_RENDERING_CTX__`). `leerProducto` (`extension/lectores/mercadolibre.js`) marcaba cualquier `sold_quantity` presente en ese JSON como "exacto", sin cruzarlo nunca contra el piso visible del subtítulo — así que "+1000 vendidos" se leyó como `sold_quantity: 1000` "confirmado", se saltó el ajuste ×2.2 (Full) que SÍ aplica Selltrix para el mismo caso, y quedó mostrado tal cual (1000, no 2200).

  **Arreglo**: nueva función pura `elegirVendidosPrincipal(soldQuantityIncrustado, vendidosAproximado)` (mismo patrón que `elegirInventarioPrincipal`, issue #251 original) — si el `sold_quantity` del JSON coincide EXACTO con el piso visible "+N vendidos", es el MISMO piso filtrándose por los dos lados, nunca un dato nuevo: se trata como aproximado, con el mismo ajuste ×2.2 Full / ×1.55 "+N" de siempre. Solo cuenta como exacto un `sold_quantity` que NO coincide con ese piso (ej. 537 confirmado cuando la ficha muestra "+500 vendidos" — ahí sí es más preciso, se respeta tal cual, sin ningún ajuste). No hace falta mantener la lista completa de umbrales que usa Mercado Libre (5, 25, 50, 100, 500, 1000, 5000, 10000, 50000…) — la igualdad directa alcanza, porque el piso visible SIEMPRE es uno de esos números por construcción (la interfaz nunca muestra un conteo exacto).

  **Alcance del arreglo**: `leerProducto` es UNA sola función, compartida por `articulo.*`, `/p/` y `/up/` (las 3 formas de ficha que ya reconoce `tipoDePagina`) — el fix vale para las 3 sin ningún código extra. Revisado (pedido explícito): Investigación (botón "Completar vendidos", `enviarVendidosAZilonix`) y Seguimiento (`enviarInventarioFichaAZilonix`) consumen `datos.vendidos`/`datos.vendidosExacto` de la MISMA `leerProducto` — ninguno de los dos vuelve a decidir "exacto" por su cuenta, así que heredan el fix automáticamente, sin tocar código del servidor. La Investigación vía listado (`lib/ml/listadoCliente.ts`, `estimarAproximadosListado`) tampoco tenía este bug: siempre pasa `exacto: false` a `vendidosEstimados` (`lib/seguimiento/aproximados.ts`) para cualquier vendido de un listado — nunca reclamó "exacto" en primer lugar. `lib/seguimiento/aproximados.ts` tampoco cambia: sus funciones son puras y reciben `exacto` como dato de entrada, la decisión real siempre vivió (y sigue viviendo) en el punto donde se LEE el dato, nunca en el cálculo.

  **Extensión subida a 0.3.37** (avisado antes de tocar `extension/`).

  **Tests nuevos** (`extension/lectores/mercadolibre.test.ts`): `elegirVendidosPrincipal` con el caso real del cojín (1000 == 1000 -> aproximado), un sold_quantity real distinto del piso (537 vs "+500" -> exacto respetado), sin JSON/sin piso, y otros umbrales reales (25, 500, 10000). Caso real de referencia completo encadenado con `calcularVentasPromedioMes`: Full -> 2200 vendidos estimados, ~50.4 ventas/mes, $4.279.716/mes (los días se despejan hacia atrás de precio+facturación, igual que los casos de referencia de `lib/seguimiento/aproximados.test.ts` — nunca se tuvo la fecha real exacta de esta publicación); un caso no Full (×1.55, nunca el mismo valor que el caso Full); y el caso de sold_quantity exacto real que NO se multiplica por ningún factor.

  Sin migraciones. `extension/` tocada (avisado antes). Sin PR (a pedido). Sin tokens de ML, sin llamadas a Mercado Libre.

- **2026-10-24** — issue #174 (Refs), bug real en vivo en staging: reconectar una cuenta de Mercado Libre reventaba con `duplicate key value violates unique constraint "cuentas_ml_cuenta_externa_unica"`. Causa real: `guardarCuentaConectada` hacía un `INSERT` simple, y `desconectarCuenta` solo marca `desconectada_ts` (nunca borra la fila, a propósito, para no perder el histórico importado) — así que la misma cuenta de ML nunca se podía volver a conectar, ni siquiera a la MISMA empresa. **Sin migración**: el índice único sobre `cuenta_id_externa` se queda igual — una cuenta de ML real sigue perteneciendo a una sola empresa de Zilonix.

  **`lib/ml/cuentas.ts` — `guardarCuentaConectada` ahora es un upsert real:** `INSERT ... ON CONFLICT (cuenta_id_externa) DO UPDATE SET ... WHERE empresa_id = <la empresa actual>` (tokens cifrados nuevos, `nickname`, `token_expira_ts`, `desconectada_ts = NULL` y `renovando_ts = NULL`). Si la fila que choca es de la MISMA empresa (conectada o desconectada), se reactiva esa misma fila — mismo `id`, se conserva el histórico de pedidos/publicaciones ya importado. Si la fila que choca es de OTRA empresa, el `WHERE` no matchea: ni el `INSERT` ni el `UPDATE` se aplican, así que no hay ninguna fila que el `RETURNING` pueda devolver.

  **Nuevo `CuentaMlDeOtraEmpresaError`**: se lanza cuando el upsert no devuelve fila (el caso normal, con RETURNING vacío) **o** cuando Postgres corta directo con `23505` — con `cuentas_ml` en `FORCE ROW LEVEL SECURITY` (`db/rls-setup.sql`), la fila conflictiva de otra empresa ni siquiera es visible para que el `DO UPDATE` la evalúe, así que Postgres puede terminar lanzando la violación de unicidad real en vez de dejar el `RETURNING` vacío — los dos casos se traducen al mismo error tipado. El mensaje (`"Esta cuenta de Mercado Libre ya está conectada a otra empresa en Zilonix. Desconéctala allá primero o escríbenos a soporte."`) **nunca revela a qué empresa pertenece**.

  **`app/api/ml/callback/route.ts` y `app/panel/conectar-ml/page.tsx`**: ya no se manda `error.message` (ni el `?error=` crudo de Mercado Libre) a la URL — 5 códigos fijos (`cuenta_en_otra_empresa`, `estado_vencido`, `ml_rechazo`, `sin_permiso`, `error_desconocido`); `page.tsx` los traduce desde un mapa cerrado, cualquier otro valor cae en el mensaje genérico, nunca se renderiza crudo. El `catch` final solo logea `error.name` (nunca el mensaje completo — `lib/ml/oauth.ts` puede meter hasta 300 caracteres de la respuesta cruda de Mercado Libre ahí).

  **Pruebas nuevas**: `lib/ml/cuentas.test.ts` — cuenta nueva inserta una fila; conectar → desconectar → reconectar la MISMA cuenta deja una sola fila activa con el mismo `id`; reconectar sin haberse desconectado antes también reactiva la misma fila; cuenta de OTRA empresa lanza `CuentaMlDeOtraEmpresaError` sin tocar la fila ajena ni el mensaje revelar la empresa. `db/rls-cuentas-ml.test.ts` — las mismas dos pruebas de reconexión/otra-empresa, pero contra Postgres real con `crearDosEmpresas()`, para confirmar el comportamiento bajo `FORCE ROW LEVEL SECURITY` que no se puede simular con un mock. `app/api/ml/callback/route.test.ts` — `CuentaMlDeOtraEmpresaError` → `error=cuenta_en_otra_empresa`; cualquier otro error → `error=error_desconocido` sin el mensaje crudo; el propio `?error=` de Mercado Libre → `error=ml_rechazo`, nunca reflejado.

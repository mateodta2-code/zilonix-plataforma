  **Corrección 2 (mismo PR, sin abrir uno nuevo): `confirmarImportacionSkus()` pasa de un `INSERT` por fila a lotes de 500** — un archivo de hasta 20.000 filas (el tope real del parser) con un `INSERT` por fila habría sido 20.000 viajes a la base dentro de una sola transacción. Las filas con nombre van en lotes con `onConflictDoUpdate({ set: { nombre: sql\`excluded.nombre\` } })` (el valor de CADA fila del lote, no uno fijo para todo el `INSERT`); las sin nombre, en lotes aparte con `onConflictDoNothing`. La consulta de "qué códigos ya existen" también se hace por lotes de 1000 (`IN (...)`). Si el mismo código apareciera dos veces entre las filas válidas (hoy no puede pasar: `importarCsvSkus()` ya descarta como error cualquier sku repetido dentro del archivo, antes de que llegue hasta acá) se deja la ÚLTIMA aparición antes de armar los lotes — un `INSERT` de Postgres no permite que el mismo conflicto se resuelva dos veces en una sola instrucción ("ON CONFLICT DO UPDATE command cannot affect row a second time"), riesgo real con lotes que no existía con el insert-por-fila de antes (cada repetido iba en su propia instrucción).

  El resumen ahora tiene 4 números, no 3: `actualizados` cuenta solo los SKU que YA existían y la fila SÍ traía nombre (de verdad cambiaron algo); los que ya existían pero la fila no traía nombre van en `sinCambios` (nuevo) — antes los dos se contaban juntos como "actualizados", aunque a los segundos `onConflictDoNothing` no les tocara ninguna columna. La pantalla muestra `sinCambios` cuando es mayor que 0.

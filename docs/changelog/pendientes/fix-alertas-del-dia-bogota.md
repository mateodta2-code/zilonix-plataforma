- **2026-10-28** — issue #204, hallazgo del PR #263: `listarAlertasDelDia` (`lib/seguimiento/seguimientos.ts`) cortaba el día en medianoche UTC en vez de Bogotá. Entre las 19:00 y las 24:00 de Bogotá, "hoy 00:00 UTC" todavía no había llegado (son las 00:00-05:00 UTC del día siguiente) — `hoy` quedaba en lo que para Bogotá todavía eran las 19:00 de HOY, así que una alerta creada HOY pero ANTES de esa hora (ej. a las 2pm) se excluía de "Alertas de hoy" en el panel, aunque para la persona en Bogotá siguiera siendo claramente de hoy. Mirado desde el otro borde (00:30 de Bogotá, recién empezado el día nuevo), el bug es el inverso: una alerta de las 11pm de AYER (Bogotá) se incluía por error en "Alertas de hoy".

  **1. Arreglo real**: `listarAlertasDelDia` ahora usa `rangoDiaBogota(new Date()).inicio` (`lib/filtros-listado.ts`) — el INSTANTE real de medianoche Bogotá (05:00 UTC ese día), correcto para comparar contra `creadoTs`, un timestamptz. Mismo criterio que ya usa `revisarUnSeguimiento` (`lib/trabajos/revisionDiariaSeguimiento.ts`) para no duplicar alertas del mismo día — nunca `fechaDiaBogota()` acá, esa da un valor de FECHA sin hora, pensado para la columna DATE `seguimiento_fotos.fecha`, no para comparar instantes.

  **2. `listarSeguimientosConFotosParaVentas` y `buscarMedicionSiExiste`** — revisadas y alineadas también, era seguro: las dos comparan contra `seguimiento_fotos.fecha` (un DATE, no un instante), así que corresponden a `fechaDiaBogota()` (no `rangoDiaBogota`). El riesgo real no era la producción (sus ventanas son anchas — ±5 días para 30d, ±2 días para 7d — una diferencia de pocas horas entre UTC y Bogotá nunca cambia qué foto cae adentro) sino el fixture de sus propios tests: `lib/seguimiento/seguimientos.test.ts` tiene un `diasAtras()` local que, hasta este cambio, truncaba en UTC — exactamente igual que la producción de antes, así que coincidían por construcción. Cambiar solo la producción sin tocar ese helper hubiera reintroducido la MISMA clase de bug intermitente que ya encontró el CI del PR #263 con `ayer` en `revisionDiariaSeguimiento.test.ts` (un desalineamiento que solo se nota en la ventana de 19:00-24:00 Bogotá). Se actualizó el `diasAtras()` del test para usar `fechaDiaBogota()` también — ahora coincide dígito a dígito con la producción, sin importar la hora real en que corra el CI.

  **3. Tests nuevos con reloj falso**, en el describe de `listarAlertasDelDia` — los dos bordes del bug, verificados con `vi.useFakeTimers({ toFake: ["Date"] })` + `vi.setSystemTime()` (solo `Date`, nunca los timers reales):

    - **00:30 de Bogotá**: una alerta de AYER a las 11pm NUNCA tiene que contar como "de hoy" (antes del fix, se incluía por error).
    - **Lección real del PR #263, aplicada**: el reloj falso se fija ANTES de crear la cuenta de Mercado Libre (`conectarCuentaMl`) y el seguimiento (`agregarSeguimiento`) — crearlos con el reloj real y recién después saltar la hora deja el token "vencido" para el reloj falso y dispara una renovación que el `fetch` mockeado no sabe responder. Sin ningún mock de renovación de token — nunca hizo falta, el token se crea ya bajo el reloj falso.

- **2026-10-28 (Refs #34)** — respaldo "sin Canva" para subir fotos: el negocio descarga su diseño de Canva (PNG, o ZIP si tiene varias páginas) y lo suelta en el "+" de la galería o de la portada por cuenta — mismo flujo real a Cloudinary que ya existía, nunca un camino nuevo. Sin migración.

  **`app/panel/publicar/fotos/zip.ts`** (nuevo) — abre el `.zip` ENTERO EN EL NAVEGADOR de la persona (`fflate`, ~8KB — nunca en el servidor: el ZIP nunca viaja completo a nuestra infraestructura, solo las imágenes ya extraídas y validadas, una por una, por el mismo endpoint de siempre). Dos pasadas a propósito:
  1. **Solo metadata** — `unzipSync` con un `filter` que SIEMPRE devuelve `false`: fflate ya lee el nombre y el tamaño ORIGINAL de cada entrada desde el encabezado real del ZIP (formato estándar, sin inflar nada) — con eso se decide qué entra (imagen válida, dentro del tope individual y del presupuesto total) ANTES de descomprimir un solo byte. Esto es la defensa real contra una "zip bomb" que pedía la tarea: nunca se mide el tamaño descomprimido DESPUÉS de inflar todo, se decide ANTES con datos que no necesitan inflar nada.
  2. **Recién ahí se infla** — solo el conjunto ya aprobado. Defensa extra (el tamaño declarado puede mentir): después de inflar se vuelve a medir el tamaño REAL de cada imagen y se confirma su firma binaria (`magic-bytes.ts`, mismo criterio de siempre) — si cualquiera de las dos falla, esa imagen puntual se omite, nunca se tira abajo el resto del ZIP.

  Se ignoran carpetas, `__MACOSX/` y cualquier archivo oculto (el patrón real `._foto.png` que macOS agrega a cualquier ZIP armado desde el Finder). Orden natural real (`1, 2, 10`, nunca alfabético puro). Límites: 20 imágenes por ZIP (`TOPE_IMAGENES_POR_ZIP`), 10MB por imagen (`TOPE_BYTES_POR_IMAGEN_ZIP`, mismo tope que ya exige cualquier foto subida a Cloudinary) y 60MB el ZIP (`TOPE_BYTES_ZIP_ARCHIVO`/`TOPE_BYTES_ZIP_DESCOMPRIMIDO` — se aplica en 2 lugares: el tamaño del archivo `.zip` tal cual se soltó, y el total descomprimido que se está dispuesto a inflar).

  **`app/panel/publicar/fotos/magic-bytes.ts`** (nuevo) — `tipoImagenPorMagicBytes` se sacó de `validar-url-externa.ts` (que sí importa `dns`/`net`, Node puro) a su propio archivo SIN ningún import de Node, para que el código de ZIP del lado del cliente también pueda usarla sin romper el bundle del navegador. `validar-url-externa.ts` la re-exporta tal cual — ningún import existente (`app/api/ml/publicar/fotos/route.ts`, sus tests) necesitó cambiar.

  **`usarSubidaFotoCloudinary.ts`** — ahora acepta VARIOS archivos a la vez (`procesarArchivos`), y cualquiera puede ser un `.zip`: se abre, se extraen las imágenes reales (en orden natural) y se suben una por una por el mismo endpoint de siempre, con progreso (`{actual, total}`, "Subiendo 3 de 8") y tolerancia a fallos — si una sube mal, las demás siguen; el error final junta cuántas fallaron, nunca un error por cada una. Nuevo estado `aviso` (informativo, nunca error) para "se tomaron solo las primeras 20", "se omitieron N imágenes por tamaño/tipo", "se tomó solo la primera imagen para la portada".

  **`GaleriaFotos.tsx`** — el input de archivo ahora acepta `.zip` y `multiple`; arrastrar/soltar también acepta varios archivos a la vez. Bug real evitado al sumar la subida de VARIAS fotos seguidas: `onChange` ahora también acepta la forma "actualizador" (como `useState`) — cada foto subida se agrega sobre el valor MÁS RECIENTE de la galería, nunca sobre una foto vieja capturada al momento del clic (con subidas secuenciales, la versión vieja hubiera pisado a la que la subida anterior ya había agregado).

  **`PortadaCuenta.tsx`** — mismo input con `.zip`/`multiple`. "En la portada solo se toma la primera imagen y se avisa" — si el ZIP (o la selección) trae más de una, `procesarArchivos(archivos, true)` sube solo la primera (orden natural si es un ZIP) y deja un aviso chico, nunca un error.

  **Diseño**: todo lo nuevo reusa `Tarjeta`/`.recuadroMarca`/`.zx-control`/`<Boton variante="secundario" chico>` y los tokens existentes (`--texto-suave`, `--kpi-peligro-texto`) — ningún color nuevo, funciona igual en claro y oscuro.
